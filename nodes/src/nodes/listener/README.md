# listener

A source node that wakes a pipeline whenever a message arrives on something it listens to, and
hands each message to the pipeline as a question. Its first source is a LaserData agent inbox.

## What it does

The Listener turns a pipeline into a long-running agent. While the pipeline runs, the selected
source delivers messages one at a time; each becomes a question on the `questions` lane, and the
pipeline's first answer goes back to whoever sent it. A message counts as handled only when the
pipeline answered it, so nothing is lost when the pipeline fails or stops mid-task. Pick it over
a webhook or chat source when other agents, not people, hand this pipeline its work.

## Lanes

| Lane in | Lane out | Description |
| --- | --- | --- |
| `_source` | `questions` | Each delivered message, as one question labelled with its sender and ids. |

## Configuration

Pick a **Source** (only LaserData today), then fill in that source's fields. For LaserData, the
**Agent id** is the one that matters: it names the inbox this pipeline works through. Most
pipelines leave **Stream** and **Max attempts** at their defaults.

### Agent id

This agent's identity: it consumes `agent.<agent_id>.inbox` in the configured stream, under
consumer group `<agent_id>`. Use lowercase letters, digits, `-` and `_` (for example `risk`). It
must match the **Agent id** of the LaserData tool node in the same pipeline, so that tasks this
agent sends name it as the sender and their replies come back to this inbox.

### Connection string

`user:password@host:port`. A `*.laserdata.cloud` host without a port gets `:8090`; any other
host must name its port, and the pipeline fails to start with a message saying so. Leave it
blank to use the `LASER_CONNECTION_STRING` environment variable.

### Stream

The LaserData stream the agent topics live in, `rocketride-memory` by default (the same default
as the LaserData tool node). Every agent in one system must use the same stream.

### Max attempts

How many times a task is retried when the pipeline fails on it (an error, or no answer) before it
is moved to the dead-letter topic. Default 3. Downtime never uses up attempts: while the pipeline
is stopped nothing reads the inbox, so tasks simply wait.

## Notes

### Working with the LaserData tool node

Agents hand each other tasks with the LaserData tool node's `laserdata.send_task` tool, which
appends a task to `agent.<to>.inbox`; the receiving agent's Listener picks it up. The pipeline
sees each task as

```
[task <task_id> conversation <conversation_id> from <sender>] <body>
```

and replies to tasks this agent sent earlier as

```
[reply from <sender> for task <task_id> conversation <conversation_id>] <body>
```

so the agent can tell new work from answers. To keep a multi-hop journey traceable as one, the
agent passes the label's `conversation_id` (and its `task_id` as `parent_task_id`) when it hands
work on. Every pickup, reply and failure is also recorded on `agent.events`, which the tool
node's `laserdata.trace` reads to show status and timings.

A minimal agent pipeline: `listener` → `agent` (with an LLM and the LaserData tool node) →
`response`. One `.pipe` can hold a webhook or chat source and a Listener side by side; each
source is started separately.

### Restarts and crashes

Stopping the pipeline stops the node process at once; nothing drains. A task that was being
handled is not acknowledged, so LaserData delivers it again when the pipeline restarts, with the
same `task_id` (`trace` then shows `attempts: 2`). Downstream side effects should therefore be
keyed on a business id rather than assuming exactly-once delivery.
