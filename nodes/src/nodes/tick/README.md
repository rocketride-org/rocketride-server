# tick

A one-shot timer **source** (`tick://`). It fires exactly once when the task starts,
writes a single text, and completes. Every other source in the catalogue is passive —
it scans a directory, or blocks waiting for an HTTP request or a chat message — so a
cron pointed at a deployed pipeline had nothing to trigger it and the task sat idle
until its ttl expired. The tick is the node that knocks on the door.

There is no interval and no repeat count. The **deploy schedule** owns recurrence: its
cron expression picks the time, the tick supplies the input, and the run ends when the
pipeline drains.

## Configuration

| Field  | Type   | Description                                                                            |
| ------ | ------ | -------------------------------------------------------------------------------------- |
| `text` | string | Message written on each fire. Empty (the default) sends the fire time in ISO 8601 UTC. |

## How it fires

The engine runs this source in DIRECT pipeline mode, where the scan feeds the render
directly:

1. When the task starts, the node reports **one** object to the engine's scan callback —
   named `tick-<YYYYMMDDTHHMMSSZ>`, sized to the text it is about to write. Reporting it
   through the callback is what feeds the engine's object counter; a source that skipped
   it would end every scheduled run with a spurious "Files not found" warning.
2. The engine opens the target pipe for that object and calls back into the node, which
   writes the text onto the `text` lane and closes the object.
3. The scan then returns. Returning is what completes the task — the engine drains the
   pipe, the process exits, and the task reaches COMPLETED. Because the run ends on its
   own, the scheduler's overlap guard clears without help and a scheduled source never
   wedges itself out of its next slot.

## Use with a deploy schedule

Give the tick source a cron expression on the team's deployment — here, 08:00 every
weekday:

```ts
await client.deploy.setSchedule(projectId, 'tick-source-id', '0 8 * * 1-5', teamId);
```

Pass `null` (or `'manual'`) as the schedule to clear it. The optional `ttl` caps the run
window; a tick pipeline normally finishes long before any ttl, so it can be left off.

## Pair with `prompt`

The tick writes one text rather than opening and closing an empty object, because an
empty object wakes nothing downstream: since #2252 the `prompt` node's `closing` returns
early when it received no input. That single write is what lets a per-close aggregator
build and emit its merged question.

The usual shape is `tick → prompt → llm_* → …`, where the prompt's saved instructions are
the real input and the tick is only the trigger. Setting **Message** turns the tick into a
parameterised ask of its own — e.g. a digest request the downstream prompt merges with its
own context.
