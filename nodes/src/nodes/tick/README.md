# tick

A source that fires once when a task starts and writes one text, so a scheduled or manual deploy run has an input to start the pipeline.

## What it does

Use the tick when nothing outside the pipeline sends data. A cron schedule or a manual `deploy run` starts the task, the tick writes one text on its `text` lane, and the task completes once the pipeline drains. Pick it over sources such as `webhook` or `chat` when the run has no payload of its own: those wait for a request or a message, so a scheduled run built on them sits idle until its ttl. The tick has no interval or repeat count; the deploy schedule's cron decides when it runs.

## Lanes

| Lane in | Lane out | Description |
| --- | --- | --- |
| `_source` | `text` | One text per run: the **Message** if set, otherwise the fire time in ISO 8601 UTC. |

## Configuration

The tick has one setting, **Message**. Most pipelines leave it empty and put the real request in a downstream node, such as a `prompt` node's saved instructions.

### Message

The text the tick writes on each run, with surrounding whitespace trimmed. When it is empty or only whitespace, the tick writes the fire time in ISO 8601 UTC instead, for example `2026-09-13T08:00:00+00:00`, so downstream nodes still get an input and know when the run fired. Set it when the tick itself should carry the request, for example `Summarize yesterday's support tickets`.

## Notes

### How it fires

The engine runs this source in DIRECT pipeline mode, where the scan feeds the render directly:

1. When the task starts, the node reports one object to the engine's scan callback, named `tick-<YYYYMMDDTHHMMSSZ>` and sized to the text it is about to write. Reporting it through the callback feeds the engine's object counter; a source that skipped it would end every scheduled run with a "Files not found" warning.
2. The callback queues the object and the scan returns; there is nothing else to report.
3. The engine opens the target pipe for the queued object and calls back into the node, which writes the text on the `text` lane and closes the object. With the scan done and the pipe drained, the task reaches COMPLETED. Because the run ends on its own, the scheduler's overlap guard clears and the next scheduled slot is not skipped.

### Use with a deploy schedule

Give the tick source a cron expression on the team's deployment. This one runs it at 08:00 every weekday:

```ts
await client.deploy.setSchedule(projectId, 'tick-source-id', '0 8 * * 1-5', teamId);
```

Pass `null` (or `'manual'`) as the schedule to clear it. The optional `ttl` caps the run window. A tick pipeline normally finishes long before any ttl, so it can be left off.

### Pair with `prompt`

The tick writes one text rather than opening and closing an empty object, because an empty object wakes nothing downstream: since #2252 the `prompt` node's `closing` returns early when it received no input. The single write is what lets a per-close aggregator build and emit its merged question.

The usual shape is `tick → prompt → llm_* → ...`, where the prompt's saved instructions are the real input and the tick is only the trigger. Setting **Message** turns the tick into a request of its own, for example a digest request that the prompt merges with its own context.

### Running the tests

```bash
python -m pytest nodes/test/tick -q
```
